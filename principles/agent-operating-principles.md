# Agent 使用原则

最后更新时间：2026-10-26

这份文件只记录已经较高频使用、且仍愿意继续采用的做法。新想法先进入实验和演进记录，
经过验证后再升级为原则。

## 1. 先给结果，再解释过程

判断一项任务是否完成，先看最终产出，而不是看执行步骤有多复杂。过程说明只保留能够帮助
核验结果、理解取舍和继续迭代的部分。

## 2. 不把推测写成事实

对 API、路径、版本、数据和引用先去验证。无法验证时明确写出“尚未验证”，并说明还缺什么
证据。推断可以用于推进工作，但不能伪装成已知事实。

## 3. 小步闭环优先

先完成最小可运行版本，再运行最接近改动的检查。只有风险或任务要求提高到相应级别时，
才扩大到全量测试、完整构建或大规模重构。

## 4. 先理解边界，再执行操作

任务开始前判断它属于问答、调研、修改、创建、排障还是评审。只做该类型正常工作需要的动作。
不因为能够执行某项操作，就默认获得了执行它的授权。

## 5. 保护已有工作

修改代码或文档前先看工作区状态和相关改动。已有改动默认属于用户，不覆盖、不回退，也不把
无关内容混进同一项变更。

## 6. 外部写操作单独确认

推送、建仓、发布、部署、创建 PR、发送消息和删除远端资源属于外部状态变化。执行前说明
目标、可见性、影响和具体动作；不确定范围时停止并询问。

## 7. 知识按寿命分层

- 原则：变化慢，回答为什么和何时适用
- 工作流：可重复，回答怎样稳定完成
- 实验：有假设和证据，回答这次是否有效
- 演进：按时间保存，回答认识如何改变

把稳定结论留在日记里，会让后来的人不断重新解释历史；把一次实验直接写成原则，则会让
知识过早固化。

## 8. 自动化只接管已经理解的重复劳动

先手工跑通一次并留下可核验证据，再提取脚本、技能或工作流。自动化必须保留失败入口，
不能把“没有报错”误判成“结果正确”。

## 9. 发布时守住身份与归属

不修改既有 Git 身份，不注入 Agent 署名，不替换版权持有人。Commit、PR 和 Release Notes
只描述实际变更，不以 Agent 为叙述主体。

## 10. 文风追求可继续维护

少用空泛口号，多写适用条件、代价、失败模式和验证方法。图表必须帮助理解关系；不需要
图表时，优先使用清晰短段落。
